Performance measurement design

Spider Shot v3
選手表現量化設計

把 60 秒 eye-frame 中心—周邊 flick 任務拆成「任務成果、控制機制、條件差異」三層。與 v2 設計的最大差別是: 機制層的 seg-v2 / phase-v1 / curve-v1 已在 TS 側落地並有凍結對表,不再是紙上路線; 但 t_detect 這條反應路徑目前被一個取樣率懸崖切斷,本文件因此改以 phase 分解為主要反應候選。

核心決策

本文件是設計提案,回答「怎麼把 v3 的資料變成可用的選手表現量化」。 每個參數的精確運算定義不在此重複 —— 見 Spider Shot v3 量測參數與意涵（參數清冊)。

D1 — 不建立單一綜合分數 預設歷史主指標只保留一項:spider-v3.peripheral-hits-per-minute。它在固定 60 秒協定下同時受搜尋、切換、命中、 回中心與逾時影響,最接近整體任務產出;但必須與首發命中率一起閱讀,否則會把連點補救誤認為高品質表現。
D2 — 反應構念改以 phase-v1 的 REC 為主要候選,t_detect 降為對照 phase-v1 的 REC 邊界讀自 seg-v2 已標記的 primary_flick 起點, 不經過 firstSustainedDecrease(),因此不共用 KI-031 的失效機制。 t_detect 保留為一致性對照（recMinusDetectMs）,不作為主要反應量。 ⚠️ 這是候選路徑,不是已驗證的替代 —— 見 R3。
D3 — 尚不定義「優秀／普通／不足」絕對門檻 2.0° 角徑與 10°–25° 角半徑仍屬未經真人 pilot 校準的候選協定值。 初期只做同一選手、同一相容 cohort 的縱向比較。
D4 — sync-v1 對 v3 結構性不適用,不列入路線圖 v3 是 translation: 'locked' + protocolGuard.noMovement,不存在 counter 事件, releaseToFireMs / counterHoldMs 沒有可錨定的對象。這不是「還沒做」,是構念不存在。

與 v2 設計的差異

v2 那份設計（2026-08-27）列出的五項「已知風險與實作前置」,到今天狀態已經不同。逐條對帳,避免延用過期前提。

v2 設計當時的陳述2026-09-09 的實況對 v3 的意義
「首發命中語意目前有誤判風險」——firstShot.hit 用整個 window 的 outcome 部分修 歷史 projector 已改為直接驗證 firstFire 的 hit outcome; 但 deriveSpiderShotMetrics().firstShot.hit 仍是 window.outcome === 'hit', 而 outcome 只要窗內任一發命中就是 'hit' 趨勢指標 peripheral-first-shot-hit-rate 可信;構念層的 firstShot.hit 會高估首發命中率,分析時不可直接使用（R2）
「Schema v1 指標文件不能直接接入 v2」—— 研究指標需先角度化、建 golden parity 已完成 seg-v2 / phase-v1 / curve-v1 / sg-seg-v2 已在 TS 側落地,並有 Python↔TS 凍結對表測試 機制層從「路線圖」變成可直接呼叫的實作,但受 C-D5 雙實作紀律約束:任一端語意變更必須兩端同步 + 重跑 golden + 版本升號
「固定 seed 可能混入序列熟悉效應」 加重 WP-58 定案:同一 drillId 的每個 rep spawn 序列逐位相同, 輪與輪之間存在練習效應,分析端不得當 i.i.d. 不只是「可能」—— 這是已入帳的契約事實。同一場 session 內的多 rep 必須以階層模型或明確的 rep index 效應處理
「Smoothness 對處理流程敏感」 仍然成立 且 SPARC／LDJ-V 只存在於 Python research/ 側,TS 無實作 SPARC／LDJ-V 不在 app 交付面,只能離線分析。第一版教練面板不得依賴它們
「方向分類不可使用 movement outcome 反推」 仍然成立且已有欄位 v3 逐顆 visible 帶 targetX/Y/Z, quadrant / side 皆由 target geometry 讀出 照用。但 side 在近垂直呈現可能只是浮點殘值,判讀前先用 quadrant 篩掉 vertical
（v2 未知） 新增 KI-031:t_detect 在 aim 更新率 < 128 Hz 時 100% 失效 切換反應與 movementTimeMs 在 < 144 Hz 顯示的 run 上靜默歸零 ⇒ D2 的路徑改變（R1）
（v2 未知） 已修 KI-021（2026-09-03）:離線 on-target 推導補齊 sphere 幾何 2026-09-03 之前的匯出其 settle／overshoot／movementTimeMs 係以 box 幾何算出,不可與修後資料合併

v3 相對 v2 的協定差異（影響量測的部分）

  • eye-frame 錨定（KI-026 / BD-026）:周邊落點以固定 scene eye (0, 1.6, 0) 生成, loadDrill() 在 arm 前驗證 eye anchor 與整個 spawn envelope。v1/v2 的眼睛未錨定問題不再存在 ⇒ 角度條件更乾淨。
  • Assessment 地位:v3 是唯一走五軸 Assessment 契約的 Spider Shot,protocol version spider-shot-v3@1.0.0 凍結。
  • condition cell 從匯出 snapshot 重建:舊資料不會被後來的 config 改動悄悄改標籤;宣稱角徑與匯出 hitbox 不符即擲錯。
  • protocolGuard.noMovement 為必要條件:缺席即無法建立 condition cell ⇒ 位移污染的 run 不可能靜默進趨勢。

三層量化模型

成果層回答「做得怎樣」,機制層回答「為什麼」,條件層回答「在哪些方向與難度發生」。

LAYER 01

任務成果

周邊 hits/min、首發命中率、命中時間。可直接用於歷史趨勢,但速度與準確率不可拆開排名。

LAYER 02

控制機制

REC／MR／V 相位、速度縮放、細修依賴、進靶逸出、正規化速度曲線。用於定位訓練方向,不直接等於成績。

LAYER 03

條件差異

依目標 D_deg、radius tier、quadrant／side 分層,並控制 trial index 與 rep index 的學習／疲勞效應。

任務難度範圍

ID = log₂(1 + D / W)；D = 10°–25°、W = 2.0°（固定）　⇒　ID ≈ 2.58 – 3.75 bits

v3 的目標角寬固定（距離恆 8 u）而角位移連續變化,所以同一位選手在同一場 60 秒內就跨越整段難度範圍 —— 這是研究 movement time 與 peak angular velocity 是否隨難度系統性調節的乾淨設計。 分析時必須使用目標條件 D_deg,而不是玩家實際 segment 位移,否則 undershoot／overshoot 會污染 predictor。

throughput 要先驗證關係再報 v3 是提示式任務（一次一顆、位置由排程給定）,沒有選擇時間混入,原則上適用 Fitts 正規化。 但 MT ~ ID 的線性必須先在資料上檢查過;throughput 是跨條件正規化的研究指標,不是 KPI。

機制與診斷指標

與 v2 設計最大的不同:下列前四項已在 TS 側落地並有 Python↔TS 凍結對表,不再是待建路線。 但它們受 C-D5 雙實作紀律約束,且對 v3 的適用性各不相同 —— 逐項給出裁決,而不是一句「可用」。

Primary Sub-movement Ratio 的修訂（沿用 v2 的判斷）

原指標是整場 segment count ratio。當分段習慣性地為每個 trial 產生「一個 primary + 一個 micro」時,結果會機械性靠近 0.5, 且多次修正的 trial 會獲得更高權重。v3 應以 trial 為分析單位,優先使用 correction-free acquisition rate; 原 ratio 僅保留研究對帳。

Velocity Scaling 的建議模型

peakOmegaDegPerSecᵢ = β₀ + β₁ × D_degᵢ + quadrantᵢ + trial_indexᵢ + rep_indexᵢ + εᵢ
  • β₁ > 0 才符合「較遠目標使用較高峰值速度」的預期
  • R² 必須與 slope 符號一起閱讀;負 slope 的高 R² 不是好表現
  • predictor 用目標 D_deg,不可用玩家實際 segment 位移
  • 至少覆蓋三個 radius tier,並回報有效 n、D range 與信賴區間
  • v3 相對 v2 新增 rep_index 項 —— 因為 WP-58 的 rep 是逐位相同的序列（見 R4）

phase-v1 用在 v3 的兩個必要調整

  • PhaseSample.side 對 v3 無意義:它讀自 peek window 的 side,而 Spider Shot 的 center-peripheral* 分支 side 恆為 'R'（佔位）。要做左右弱側分析,必須改用 deriveSpiderShotTransitions() 的 eye-frame side,不能用 phase 樣本自帶的那個欄位。
  • V 相位的語意在 v3 更重要:v3 沒有 counter-strafe 的煞停需求,所以 V（MR 結束 → 首發）幾乎純粹是 「敢不敢開槍」的驗證時間。V 長而首發命中率高 = 過度確認;V 短而角誤差大 = 開火太早。這是 v2 設計裡沒有的診斷軸。

教練解讀方式

先用 hits/min 與首發命中率判斷速度—準確率型態,再用相位、落點、停止與曲線形狀找原因。

高產出 × 高首發率

快速且首發可靠。再看遠距 tier 與弱側（eye-frame side）是否仍維持;避免只因固定 seed 熟悉序列而下結論。

高產出 × 低首發率

速度偏置或以連點補救。優先看首發角誤差、逾時率、correction-free rate 與逸出角度;curve-v1 會顯示右偏多峰。

低產出 × 高首發率

可能過度保守。用 phase-v1 拆 REC／MR／V:V 相位偏長即過度確認。再看 peak velocity 是否隨 D_deg 放大。

低產出 × 低首發率

先排除資料品質與設備相容性（特別是顯示刷新率）,再依 REC → MR 落點 → 停止控制 → 細修依賴的順序診斷。

建議的診斷順序

  1. 確認 quality gate、meta.displayHz ≥ 144、完整 60 秒、有效周邊呈現數
  2. 看 hits/min 與首發命中率的速度—準確率組合
  3. 用命中時間拆出整體切換效率,再用 phase-v1 的 REC／MR／V 定位是反應、執行還是確認
  4. 用首發角誤差、逸出角度、correction-free rate 判斷落點與停止控制
  5. 用 curve-v1 的集群平均看速度曲線形狀,再用 velocity scaling 解釋動作策略 —— 不直接貼能力標籤
  6. 依 D_deg、radius tier、quadrant／side、trial index、rep index 檢查特定方向、難度、學習或疲勞效應
不可進教練報告的東西 未通過構念驗證（reliability gate）的指標不得進教練報告 —— 寧可少一個指標,不能有一個會說錯話的指標（C-D3 / GD-20）。 以現況,本文件所列的每一個指標都還沒有信度證據,所以第一版只能作縱向自我比較,不能作處方依據。

資料與相容性契約

分析單位

成果與機制指標的基本單位是一次 center → peripheral transition 對應的周邊目標窗。 所有 segment、fire、hit、tracking sample 與目標條件必須透過 targetId 或明確 window anchor 對齊, 禁止以純時間鄰近猜測歸屬。回中心的呈現只作為節奏錨點,不產出逐 trial 構念。

Session-level condition cell

spider-v3:frame=eye-v1;scene=spider-shot-room;eye=0,1.6,0;distance=8u;peripheral-distance=8-8u;radius=10-25deg;width=2deg;grid=4x3;shape=sphere;translation=locked

歷史 cohort 使用這個從不可變匯出 snapshot 重建的整場身分。 每一次實際 transition 的連續 D_deg、方位角與 seed 位置僅用於 per-target 分層與迴歸, 不應把單一 trial 的 spider:d=…;w=… 當作整場 cohort identity。

Condition attribution

  • 距離:使用目標幾何推導的 D_deg,並對映至三個 radius tier
  • 方向:使用 eye-frame 的 quadrant／side;不可用實際 mouse path 的 dx/dy 反推
  • 兩套分類不可混用:spawn 用的 4 象限分箱（0/90/180/270 起算）與呈現層的 horizontal／vertical／oblique（45° 居中）是刻意不對齊的兩套分類,報告需明確命名是哪一套
  • 難度:保留連續 D／W 與 Fitts ID,不只存 near／mid／far 標籤
  • rep:記錄 rep index;同一 drillId 的多 rep 序列逐位相同,不是獨立取樣

版本與升級紀律

  • 趨勢指標語意或參數變更 ⇒ registry version 升號,不得原地改語意
  • seg-v2 / phase-v1 / curve-v1 / sg-seg-v2 任一端變更 ⇒ C-D5:兩端同步 + 重跑 golden 產生腳本 + promoted-*.test.ts 全綠 + 版本字串升號
  • 任何處理流程（sampling／filter／resampling／segmentation／speed source）改變 ⇒ 不與舊值畫同一條趨勢線

真人 pilot 與統計驗證

指標方向合理不代表已具構念效度。正式門檻與訓練建議必須建立在可重複的真人資料上。

階段最低建議主要檢查輸出

2. Test–retest pilot多位選手、每人多日重測ICC、SEM、MDC、session learning可信變化幅度（MDC）
3. 構念驗證不同技術層級、受控難度D/W 效應、速度—準確率、收斂／區辨效度保留或淘汰指標（C-D3 閘）
4. 教練門檻完成前述信度與效度後實務效果量、誤判成本、跨設備泛化版本化門檻與建議
階段 0 是 v3 特有的,不可略過 v2 的驗證計畫從「單人 baseline」開始。v3 必須先跑階段 0,因為 KI-031 讓兩類構念在低刷新率上靜默歸零 —— 在確認資料真的有值之前,任何 baseline 的「中位數」都可能是空集合的假象。

每場最低資料門檻（暫定）

  • 首發命中率:至少 20 個完整周邊呈現
  • 命中時間／角度誤差／逸出角度:至少 10 個有效樣本,並顯示 n
  • Velocity scaling:至少 20 個有效 primary flick、涵蓋 3 個 tier,且 D_deg 有足夠變異
  • phase-v1:每個呈現窗至少 30 tick（實作的 PHASE_MIN_WINDOW_TICKS）,否則該樣本退化
  • curve-v1:每個呈現窗至少 3 tick 才重取樣
  • 單一 12-cell 細分若 n 過低,不顯示好壞判斷;跨 run pooling 或使用階層模型

以上 n 門檻是工程與閱讀安全起點,不是經 power analysis 或真人 pilot 凍結的標準。 參考量級:一份 60 秒 spider-shot-wide-v1 真人 run 實測為 34 個周邊到達;v3 幅度較小、節奏應更快, 預期更多,但尚未實測。

已知風險與實作前置

R1 — KI-031:t_detect 在 < 144 Hz 顯示上 100% 失效（🔴 未修） firstSustainedDecrease() 要求 4 個連續合格樣本,隱含「每個 sim tick 的 aim 都更新」這個從未寫下的前提。 60 Hz 顯示下 aim 約每兩個 tick 更新一次 ⇒ 負值與 0 嚴格交替 ⇒ 四份真人匯出的 113 個周邊呈現,detected 為 0 / 113。 而 status: 'timeout' 是合法值,所以失效完全靜默:一份 100% timeout 的 run 看起來像「這位選手完全沒反應」。
⇒ 採集紀律:v3 只在 meta.displayHz ≥ 144 的機器上錄。修法屬 BD-031,是 C-D5 雙實作變更,不在本設計範圍。
R2 — firstShot.hit 會高估首發命中率（構念層未修） buildPeekWindows() 的 outcome 規則是「窗內任一發命中即 'hit'」, 而 deriveSpiderShotMetrics().firstShot.hit 直接取 window.outcome === 'hit'。 於是「首發 miss、補槍命中」會被記成首發命中。
⇒ 歷史指標 peripheral-first-shot-hit-rate 不受影響（projector 直接驗證 firstFire）; 但任何直接讀構念層 firstShot.hit 的分析都必須自行改用 firstFire 的 hit outcome。
R3 — phase-v1 對取樣率的免疫性尚未驗證 REC 邊界不經 t_detect,所以不共用 KI-031 的機制。但 seg-v2 同樣吃逐 tick ω, 而低刷新率下 ω 呈高／零交替 —— 這對 sg-seg-v2 平滑後的偵峰會有什麼影響,沒有人量過。 D2 是候選路徑,必須由驗證階段 0 在同一份 60 Hz 資料上證實或推翻,不得假設免疫。
R4 — 固定 seed + 逐位相同的 rep 同一 drillId 對應同一組 seeded config,逐輪 spawn 序列逐位相同,輪與輪之間存在練習效應。 固定 seed 有利 test–retest 標準化,但長期重複會讓「進步」部分來自熟悉同一序列,而非一般化 flick 能力。
⇒ pilot 必須估計 run index 與 rep index 效應;若日後採多 seed,需版本化 seed-set,而非任意改動。
R5 — phase-v1 / curve-v1 的真人證據基礎極窄 現有實證僅涵蓋一位匿名受試者（P001）、三個 session、一台 240 Hz 機器、一個 drill config, 且那個 config 不是 v3（是 counter-strafe 家族）。這不是 population-level 效度。 「REC-end 與 t_detect 相差 9–11 tick」這類數值不可當成固定校正係數。
R6 — quality gate 目前很弱 checkQualityGate() 用 visible 事件數,而 minN = 1 —— 實際上幾乎不篩任何東西。 它能擋 suspect 與不相容 protocol,但不是樣本量保證。上面的每場 n 門檻必須在分析層自行落實。
R7 — 平滑度與分段對處理流程敏感 SPARC、LDJ-V 與 seg-v2 均受 segmentation、sampling、resampling、filtering、訊號雜訊與退化 sentinel 規則影響。 任何處理定義改變都必須升 metric version,不與舊值直接畫同一條趨勢線（C-D5）。 Spider Shot 是 flick-heavy 任務,n_tracking = 0 不代表選手沒有 tracking 能力。
R8 — 逸出角度無方向、方向欄位有浮點陷阱 overshootDeg 是無號值,衝過頭與沒到位在資料上不可分（刻意取捨,避免第二套有號幾何,C-D4）。 eye-frame side 在近垂直呈現可能只是浮點殘值（sin(180°) = 1.22e-16）⇒ 判讀前先用 quadrant 篩掉 vertical。
R9 — 跨 KI-021 修復日不可合併 2026-09-03 之前的匯出,其 settle／逸出角度／movementTimeMs 係以外接立方體幾何算出 （對角方向最多寬鬆 √2 倍）。不可與修後資料畫同一條趨勢線。

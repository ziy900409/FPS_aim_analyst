01 · 結論

同一批資料，兩種指標，完全相反的排名

提案的 Layer A 會把最差的一場評為最好。

第三場（08.932Z）的中位命中時間 860 ms（三場最快）、總命中率 36.7 hits/min（三場最高）—— 提案的三個主結果有兩個把它排第一。但它的首發命中率只有 82.9%，其餘兩場是 97.0% / 97.1%。 把命中改成「首發命中」後，它的產出是 30.4 首發命中/分，三場最低。 玩家不是變強了，是把工作點往「更用力、更早開槍」推，然後用補槍把數字補回來。

提案主指標排名

  1. 08.932Z — 860 ms · 36.7/min ← 實際最差
  2. 53.218Z — 891 ms · 34.8/min
  3. 24.700Z — 907 ms · 34.2/min

首發有效速度排名

  1. 53.218Z — 34.8 首發命中/min
  2. 24.700Z — 33.2 首發命中/min
  3. 08.932Z — 30.4 首發命中/min

單一改動就能修掉它：主結果只認 window.firstFire.hit，不要用 deriveSpiderShotMetrics().firstShot.hit。後者取的是 PeekWindowTs.outcome，規則是 「窗內任一發命中即 hit」，於是首發失手＋補槍命中會被記成首發命中——在這 103 筆上它回報 102/102 = 100%，是一個完全沒有變異的指標。真值是 95/102。這與 spider-shot-v3 教練報告已經踩過的同一個坑（HANDOFF §3.3 ①）。

02 · 條件

先修正三個關於這支 drill 的描述

提案把任務描述成「約 40–70° yaw」的角距劑量反應任務。這在這個硬體條件下不成立，而且不成立是設計本身決定的： resolveSpiderWideYawPitch() 在 arm 時用當下的 FOV 與 aspect 解析一次 yaw 窗， FOV 75 + aspect 1.778125 解出的是 [47.5086, 51.6397]，下界係數 kLo = 0.92。 三份 run 的 resolvedFrom 逐位相同。

04 · 主結果

一個數字：首發有效速度

沿用 spider-shot-v3 教練報告已凍結的 M1 定義，不另發明： 首發命中數 ÷ 有效周邊呈現時間。分母是 intention-to-test —— 未開火、逾時、補槍命中的 trial 全部留在分母。它一個數字同時懲罰「慢」與「亂」，這正是提案把速度與準確度拆成兩個並列主結果之後 失去的性質。

Run 1 · 24.700Z 33.2 首發命中/min · 32/33 = 97.0%
中位命中 907 ms
Run 2 · 53.218Z 34.8 首發命中/min · 34/35 = 97.1%
中位命中 891 ms
Run 3 · 08.932Z 30.4 首發命中/min · 29/35 = 82.9%
中位命中 860 ms

單場 n≈35 撐不起「進步」的判語。三場之間 33.2 → 34.8 → 30.4 的落差，在沒有 test–retest reliability 與 MDC（最小可偵測變化）之前不能稱為變好或變壞。本文所有圖只回答 「這場發生了什麼」，不回答「他是不是變強了」——後者需要 v3 教練報告已列的 MDC band，而 MDC band 需要同條件的多場基準（本批總共 3 場，不足）。

06 · 版面

一頁式：從「能不能讀」到「怎麼練」

提案用四個分頁（總覽／單次 Flick／左右差／資料品質）。分頁的代價是教練必須先知道要點哪一頁才能發現問題， 而且首屏截圖只剩一頁。改為單頁五帶、由上到下就是判讀順序；左右差不給獨立分頁，因為本批沒有可報的左右差。

帶 1 · 閘門 這場能不能解讀（W5）

不可解讀就停在這裡，不往下顯示任何能力數字。含明確的「不可算」欄位。

帶 2 · 一個數字 首發有效速度 M1 + ITT 分母

單一 hero 數字，旁邊永遠並列 n 與首發率。不顯示歷史趨勢或玩家等級（practice-only）。

帶 3 · 工作點 W1 速度—準確率 + W2 失手分解

並排。W1 說「工作點動了沒」，W2 說「動的代價長什麼樣」。這一帶回答 90% 的教練提問。

帶 4 · 機制 W4 峰值角速度 × 首發結果

把 W2 的機制轉成可執行的指令（降速／改變開槍時機）。

帶 5 · 個案 W3 逐 trial 時序（可選 trial）

最後才展開。教練用它向選手展示單次失手實際發生了什麼，也是唯一需要互動選擇的圖。

三條教練紀律（沿用 v3 教練報告）： ① 任一格 n < 8 只列數字、不上色、不下結論； ② 未通過構念驗證的指標不進教練面（C-D3）； ③ 每個數字旁邊必須有它的 n 與分母定義——spider-shot-wide-v1 是 practice-only， 不寫入 participant 歷史、不產生 compatibility cell、不進 DrillMetricRegistry。

07 · 邊界

這批資料還不能說的話

提案在這一節的立場是對的（不做總分、不做玩家等級、要真人資料），下面只把它收斂到本批的具體數字上， 並補三條提案沒有預期到的限制。

  • 不能說「變快了」或「變慢了」。n=1 玩家、單一硬體、3 場、同一顆 seed 57001。沒有 test–retest、沒有 SEM/MDC。
  • 不能說左右差。Δ7 ms、n≈50/側 —— 這是「無證據」，不是「無差異」，更不是「左側弱項」。
  • 不能報角距斜率或 Fitts throughput。D 只有 4.16° 跨距。要做劑量反應，得另開一支刻意分層多個 yaw 帶的排程。
  • 不能報實體滑鼠行程。meta.dpi 缺席；只有 countsPer360 = 11688.3 可稽核。錄製規格要求的 DPI 欄位沒有落進匯出，這是下一批錄製前必須修的。
  • 不能說「沒有抬滑鼠」。0/103 只代表 150 ms / 2 deg/s 門檻在 240 Hz 這台機器上沒有觸發；該門檻是 60 Hz 機器校出來的，且 KI-033 已知會漏 acquisition failure。
  • 不能把 120 ms 敏感度分析當成 canonical reaction。它把 coverage 補到 103/103，卻仍取自前一個 presentation 的尾段，且本批 baselineInsufficient 為 103/103。正式 baseline 契約修好前，只能在同參數的敏感度分析內比較。
  • 三場不可視為獨立重複。間隔各約 2.5 分鐘、同一 session、同一 seed，順序效應與疲勞和 run 編號共線。Run 3 的工作點漂移有可能就是疲勞，本批無法分離。

對「需要真人資料嗎」的回答沒有改變，但門檻更清楚了。本批已足以否證兩件事 （提案的 Layer A 排名可信、240 Hz 就足以保證 canonical reaction 可用）；並揭露 KI-034 的快速週期 baseline 污染。不足以建立任何常模、權重或個人特徵。 提案的 Stage A 5–8 人 × 2 runs 仍是正確的下一步，但錄製規格必須先補 DPI 與滑鼠取樣率欄位， 否則 Layer D 的共變量一批都算不出來。

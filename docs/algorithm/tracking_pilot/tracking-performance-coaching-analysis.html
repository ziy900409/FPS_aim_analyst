§ 1tracking 不是一個能力,是四個

教練最常犯的錯是把「跟槍不好」當成單一診斷。在本專案的資料結構裡,一次 tracking presentation 被明確切成四段互不污染的構念,每段有自己的指標、自己的失敗模式、自己的處方。混在一起看, 處方一定開錯。

① ACQUISITION

抓得到嗎

目標出現到第一次瞄準線真的穿過 hitbox 的時間。這一段是 flick 能力, 刻意與跟隨分離,免得「找目標慢」被誤讀成「跟不住」。

② STEADY PURSUIT

跟得住嗎

取得之後把準心留在目標上的能力。這才是 tracking 的本體,而且只在 [first_on_target, 窗尾) 內計算。

③ REACTIVE CORRECTION

目標變向時反應多快

只有 reversal 家族才有這一段。量的是「刺激突變後的暫態」,與穩態誤差是不同的肌肉。

④ RECOVERY

掉了救不救得回

掉出目標的頻率、救回來的次數、以及最長一次失聯。「掉很多但都救回來」和 「掉一次就再也沒回來」是兩種完全不同的選手。

§ 2分析前的三道門:資料有效 → 刺激保真 → 條件可分辨

這一節放在指標之前,因為它救過這個專案好幾次。在這三道門之前算出來的任何漂亮數字都是垃圾, 而且是會騙人的垃圾——它們看起來完全正常。

門 1:run-level eligibility(資料本身可不可信)

evaluateTrackingRunEligibility(payload) 在任何指標推導之前跑,回傳一個封閉的 8 碼 TrackingQualityReason 詞彙表。它不會在第一個失敗就短路——一個 run 可以同時 overflow 又 coverage 不足,兩者都必須被看見。

Reason code觸發條件教練該怎麼處置
recorder-overflowmeta.recorderOverflow === true整個 run 作廢,重跑。不要「就用前半段」
input-buffer-overflowmeta.bufferOverflow === true同上;通常是機器負載,先關背景程式
missing-scored-start沒有任何 scored_start event協定沒跑對,沒有計分窗可言
missing-target-position計分窗內有 tick 的 tx/ty/tz === null刺激軌跡有洞,作廢
non-monotonic-timestamps時間戳非嚴格遞增(依原始錄製順序檢查,不重排)時鐘域出事,作廢並回報
insufficient-scored-coverage計分窗 tick 覆蓋率 < 99.5%(NFR-54-4)掉 frame/掉 tick;25 s 窗容許不到 16 tick 的缺口
unsupported-schema-versionmeta.schemaVersion !== 2舊格式,不可與現行資料混
unrecognized-tracking-trajectorymeta.spawn.trackingTrajectory.kind 不是 band-limited-2d-v1/reversal-2d-v1不是本協定的刺激

另有 tracking-pilot-v2 專屬的 held-fire 覆蓋率:計分窗內 ticks[].fire === true 的比例,只對 meta.protocolGuard.requireFire === true 的 run 計算,門檻 ≥ 0.95(25 s 容許約 1.25 s 放開)。選手沒按住左鍵就等於沒在做這個任務。

門 2:刺激保真度(選手實際看到的,是不是你以為的)

這是本專案最貴的一課

KI-024 之前,field-low 場景的眼睛沒有錨定在 sim origin,交戰距離是 8 u 而不是 config 的 4 u ⇒ 每一個角度量(目標角尺寸、行程振幅、角速度)都只交付了一半。 metadata 仍然誠實地寫著「0.5°、5 deg/s」,eligibility 全綠,指標全部算得出來—— 只是選手看到的是 0.25° 與 2.5 deg/s。沒有任何指標層的檢查能抓到這件事,只有去量錄下來的位置才能。

因此分析 runner 有一層 measureTrackingDeliveredAngles()(layer 4), 從錄到的 tx/ty/tz 與 meta.scene.eye反推選手眼中的實際交戰距離、 交付速度與角尺寸,逐 run 印出「交付/宣稱」比。現行 G6 世代的健康值是 100–103%。

刺激已經換過六個世代,跨世代的資料不可合併比較,而且 drillId 有跨世代重用 (..._2deg_5dps 在 G1–G4 是大尺寸層、在 G5 是小尺寸層)。最可靠的世代辨識:

世代辨識能不能拿來當教練依據
G1frequencyBandHz [0.1,0.7] + yawBoundDeg ≤ 2不能
G2[0.3,2.1] + 每 cell 有自己的 hitbox不能 速度須 ×√2(calibration 除外)
G3meta.scene.eye.z === 4不能 所有角度量 ×2
G4eye.z === 0 + [0.15,1.05] + speed 5/14刺激正確 但尺寸層已被 revise
G5同 G4,size 候選 3.0 / 2.0 deg刺激正確 任務為「禁止開火」
G6(現行)meta.weaponId === 'tracking_pilot_hold' + protocolGuard 為 {requireFire, noMovement}現行唯一可用
G5 → G6 是特別的一條界線

前五代的分界都是「同一個任務、刺激交付錯了」。G5→G6 是唯一一次刺激幾何逐位完全相同、 但任務本身換了:選手現在要全程按住左鍵一邊追蹤。雙任務負荷會壓低所有 P0/P1 指標, 量級未知。刺激保真度那一層攔不下這一組(軌跡確實一模一樣),只能靠 weaponId/protocolGuard 判代。

門 3:條件可分辨性(這個 cell 到底測不測得出東西)

這是我認為對教練最重要、也最反直覺的一道門。把準心凍結在選手自己 aim 的中位數上, 用同一個 ε 定義、同一個計分窗重算一次:

ratio = RMS ε(凍結準心) / RMS ε(實際)

這個比值是該條件可分辨性的上界。比值趨近 1,表示「完全不動」和「認真跟槍」算出來的 誤差差不多——無論儀器多忠實,這個條件就是測不出跟槍能力。實作: scripts/trackingFrozenCrosshairRatio.ts(runner layer 5)。

Gate A 第三輪的實測非常說明問題:reversal 家族 2.06–3.01(唯一已證實有效), 20 deg/s cell 1.40–1.52,而 5 deg/s 的三個 cell 與兩個 axis calibration 只有 1.08–1.35 ——那些 cell 測不出跟槍能力。依 C-D3(未通過構念驗證的指標不得進教練報告), 這些 cell 的數字不准拿去跟選手講。

同一個道理的另一面

totPercent = 100% 不是好消息,是壞消息。G1 世代所有 cell 的 TOT 恆為 100%,因為目標角尺寸全都約 ±7°——指標飽和,零資訊量。反過來,2026-09-04 乾跑顯示 0.5° 雙軸 cell 的 TOT 只有 1.5%/3.9%,低於 5% 的 hard floor(地板效應,同樣零資訊量)。有用的區間在中間。

§ 3P0:任務層表現(選手做到了什麼)

P0 是「結果」層,全部從 raw tick 離線推導,引擎不做任何額外計算、不引入任何新閾值 (GD-7)。實作:src/metrics/trackingDerivation.ts。

on-target(t) — 一切的基礎

box    = [tx±w/2] × [ty±h/2] × [tz±d/2]
sphere = { p : |p − (tx,ty,tz)| ≤ w/2 }        // 三軸必須相等
on-target(t) = ray(p_eye, f_aim) 與該實體在 s ≥ 0 相交

這與引擎命中判定是同一個幾何(THREE.Ray.intersectBox/intersectSphere, 單一來源 meta.targets.hitbox)。沒有「on-target 容許角」這種可調參數:on-target 的字面意思就是 「這個 tick 沿瞄準線開一槍會不會中」。

ε(t) — 連續誤差

ε(t) = acos( clamp( dot( norm(f_aim), norm(p_target − p_eye) ), −1, 1 ) )   // 度

眼睛是所有角度量的頂點:p_eye = eyeBase + (px, 0, pz) × simToWorld。

指標定義教練讀法
tAcquireMs P0 t_first_on_target − t_visible flick/定位速度。與跟隨完全分開,不要合成一個分數
acquisitionFailure / acquisitionFailureRate 整個 presentation 從未 on-target 是有效的觀測結果,不是缺資料。該 presentation 排除在 TOT/ε 聚合外,但計入失敗率
totPercent P0 計分窗內 on-target tick 佔比 最直觀的「跟得住」。注意飽和(→100%)與地板(<5%)兩端都無意義
rmsEpsilonDeg 預註冊主要統計量 sqrt(mean(ε²)),僅計分窗內 之所以選 RMS 而非 mean:對「丟失目標的那一瞬間」二次敏感——正是教練關心的失誤
medianEpsilonDegε 中位數典型狀態下的精度,不受少數大失誤影響
p95EpsilonDegε 第 95 百分位最壞情況。median 低但 P95 高 = 平時很穩、偶爾大崩
為什麼 median 與 P95 值得一起看

rmsEpsilonDeg 是單一數字,而 median/P95 的落差直接告訴你 「這位選手的問題是基礎精度,還是穩定性」。基礎精度差 → median 高;穩定性差 → median 低而 P95 高。 兩者的訓練處方完全不同。

§ 4P1:控制層機制(選手為什麼做到/做不到)

P0 告訴你結果,P1 告訴你機制。這是教練真正能開處方的層。實作: src/metrics/trackingDynamics.ts 的 deriveTrackingDynamics()。

lag 與 gain:把「跟不住」拆成兩個獨立故障

corr( ω_target(t), ω_aim(t+τ) )  在 τ ∈ [0, 250] ms 上取最大   // τ 量化到整 sim tick
τ̂ > 0  ⇒  aim 落後 target

velocity_gain = Σ dot( ω_target(t), ω_aim(t+τ̂) ) / Σ dot( ω_target(t), ω_target(t) )
velocity_rmse = ω_aim(t+τ̂) − gain · ω_target(t) 的殘差 RMS 大小

關鍵在於 ω_aim 讀的是 tick.dYaw/dPitch(tick 窗內積分的滑鼠位移), 不是對 aim.yaw 做差分——避開 render/sim 節拍的 aliasing(KI-005)。

LAG_MS

時間軸的故障

你比目標慢多少。高 lag = 反應性跟隨(等目標動了才跟),缺前饋/預測。

VELOCITY_GAIN

幅度軸的故障

<1 = 跟得不夠遠(手速不足或不敢動);>1 = 動過頭。

VELOCITY_RMSE

平滑度的故障

lag 與 gain 都對之後剩下的誤差。高 = 抖動、微調不平滑,通常是硬體/握姿。

lag-peak-ambiguous — 一個很重要的拒答

如果相關性 vs τ 曲線的第二高峰超過最高峰的 1/2,結果直接 blocked。 週期性訊號不可以靜默地收斂到某一個 lag 值。這是刻意設計的:寧可沒有數字, 也不能給教練一個「看起來合理但是錯的」lag。

signed bias:系統性偏移

signed_yaw_bias_deg   = mean( wrap( aim_yaw(t) − target_yaw(t) ) )    // 計分窗內
signed_pitch_bias_deg = mean( wrap( aim_pitch(t) − target_pitch(t) ) )

正 yaw = 準心偏在目標右邊;正 pitch = 偏上。兩個獨立的帶符號數字,絕不正規化成一個純量, 也絕不與 lag/gain 合成 composite score。這對教練是好事——「你習慣壓右邊」是可執行的回饋, 「你的 tracking 分數 72」不是。

recovery:掉出目標之後

欄位意義教練讀法
dropRatePerSecdropCount / pursuitDurationSec脫離頻率。單看它不足以判難易
completedReacquireCount掉了又救回來的次數高 = 修正機制健康
terminalDropCountdropCount − reacquireMs.length,最後那次沒救回來≥1 就是警訊:難度可能超出
longestOffTargetMs最長一段連續 off-target(含未復原的尾段)獨立欄位,絕不併入 reacquire。這是「失聯多久」

time-on-task Δ:這 25 秒裡表現有沒有漂

Δ = ( RMS ε(最後 5 s) − RMS ε(最前 5 s) ) / RMS ε(最前 5 s)

同一個計分窗內取頭尾各 5 s(128 Hz 下各恰好 640 tick)。窗跨度 < 10 s 直接回 window-too-short 不給數字——否則兩半重疊,Δ 有一部分是拿同一段資料跟自己比。 判準是 cell 層平均 |Δ| ≤ 20%,逐 run 印出只是為了讓操作員在平均掉之前看見異常的那一個 run。

教練用途

Δ 是耐力/專注指標,不是能力指標。Δ 明顯為正 = block 太長或選手續航不足(縮短 block、加休息); Δ 明顯為負 = 前段還在暖身(加 practice block)。把衰退讀成「能力差」是誤診。

Blocked 優先序

deriveTrackingDynamics 依此順序判定,前面的資料問題永遠壓過後面的: protocol-incompatible(計分窗內有 protocol_violation)→ no-acquisition → missing-target-telemetry → insufficient-valid-ticks → lag-peak-ambiguous。

注意這與 §2 的 run-level eligibility 是兩套刻意不合併的封閉詞彙表: 同一個概念在兩層用不同名字(missing-target-position vs missing-target-telemetry)。 一個 run 可以在 eligibility 層合格、卻在 P1 層 metric-blocked。

§ 5換向事件:唯一已證實有效的條件

deriveTrackingReversalWindows() 是另一個獨立函式,窗界落在 target_motion_change event 上。核心矩陣(pursuit)本來就會產生零個 change event ⇒ 回傳 { windows: [] },這是正常空集合,不是 blocked。

指標讀法對應能力
responseLatencyMsε 首次超出 baseline 一個小固定邊際的時刻換向偵測速度(視覺→運動)
peakErrorDeg可用窗內 ε 的最大值最壞暫態偏離
overshootDegmax(peak − baseline, 0)暫態幅度,已扣掉穩態水準
settlingTimeMsε 回到容忍帶內且維持到窗尾修正的收斂能力

被排除的 change 有具名理由,不會靜默消失:'insufficient-window-data'(可用窗短於 minWindowMs)、'overlap'(距上一次 change 不足 minBaselineMs, 拿不到乾淨 baseline)。

為什麼教練現在該優先用 reversal

Gate A 實測的凍結準心比值:reversal 2.06–3.01,而 5 deg/s 的核心 cell 只有 1.08–1.35。 reversal 是目前唯一已證實「測得出跟槍能力」的家族。如果你今天只能收一種資料,收 reversal。

§ 6教練診斷矩陣:指標樣態 → 診斷 → 處方

單一指標幾乎不能開處方,組合才能。下表是我實際會用的讀法。左欄的每個欄位都是上面 定義過的既有欄位,沒有新構念。

BR 條件的特別警告

tracking_br_v1 系列有 ADS 與彈道(projectile)。它的 export 會同時給你 aimRayOnTargetRate(瞄準線在目標上的比例)與 ballistic hit(子彈是否命中)—— 兩者刻意分欄,pure tracking summary 絕不讀 hit count / damage / kill。 用命中數當跟槍指標會把彈道飛行時間、提前量、武器參數全部混進「跟槍能力」裡。 想評跟槍,看 aimRayOnTargetRate;想評彈道提前量,那是另一個構念。

§ 7原始資料 → 指標對照表

本專案的引擎只錄 raw v2 ticks/events,所有指標離線推導(GD-7:raw-over-derived)。 以下是每個教練判斷實際吃的欄位。

逐 tick(ticks[],128 Hz)

欄位內容餵給誰
tms,performance.now() 時鐘域所有時間量;非嚴格遞增 ⇒ run 作廢

§ 9現在還不能對選手說的話

這一節與前面同等重要。一個會說錯話的指標比沒有指標更糟。

C-D3 紅線

沒有百分位、沒有常模

WP-54 的 T7(難度校準,12–20 人)與 T8(重測信度:ICC / CV·SEM / Bland-Altman)都還沒開工。 現在說「你在 tracking 上是前 20%」是無依據的。只能說「你這次比上次的 RMS ε 低」。

D-S11-5

沒有 composite score

不做跨構念綜合分數。lag、gain、bias、TOT 必須分層呈現。把它們壓成一個「跟槍分」會讓 處方無法回推。

Gate A 部分通過

核心矩陣參數未校準

band-limited 核心 2×2 矩陣被退回 T7 重新參數化(凍結準心比值在原頻帶下上界只有 1.61, 達不到 2.0 門檻)。reversal 家族是目前唯一已證實有效的。

C-D4

不得有第二套定義

ε(t) / on-target / 計分窗 的權威在 docs/operational/analysis-*.md + src/metrics/。任何分析腳本自己再算一套 ε,即為 bug。

不要做的四件事

  • 不要合併跨世代資料而不標註世代。G3 的角度量要 ×2,G2 的速度要 ×√2(calibration 除外), 而 drillId 跨世代重用過。
  • 不要讀凍結準心比值 < 2.0 的 cell。那個 cell 的漂亮數字不代表選手能力。
  • 不要用 hit/damage/kill 當跟槍指標。BR 條件的 ballistic 命中與 aimRayOnTargetRate 是分欄的兩個構念。
  • 不要把 blocked 當 0。no-acquisition、lag-peak-ambiguous、 insufficient-scored-coverage 是三種完全不同的處置,每一種都不是「表現差」。
現在可以誠實說的話

在 G6 世代、eligibility 全綠、凍結準心比值 ≥ 2 的 reversal cell 上,對同一位選手的 session 內或 session 間變化做敘述性比較,並用 §6 的組合樣態指出機制層的缺口 (「你的問題是 gain 不足而不是反應慢」)。這是目前資料真正支撐得起的教練結論。

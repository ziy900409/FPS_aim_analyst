Algorithm discussion draft · v0.3

Peek Click Transfer
個人每日訓練診斷演算法

本文件把 peek_click_transfer_pilot_v1_2deg 定位為個人縱向診斷工具： 不與其他選手排名、不產生 composite score，而是判斷今天相對於自己的近期穩定狀態， 並沿著動作鏈找出最早出現的問題。

對象：單一選手 頻率：每日 固定條件：2° / 20 presentations / strict L-R 已確認：首發速度低於 accuracy threshold 才算急停成功 狀態：討論稿，尚未凍結
設計原則 演算法流程 指標契約 策略辨識 個人基準 診斷規則 每日輸出 風險 待討論

1. 設計原則

核心目標：在不犧牲有效首發率的前提下，逐步縮短曝光到首發的時間； 若結果惡化，指出動作鏈中最早發生的異常環節。

個人縱向，而非常模排名

所有「變好／變差」都比較選手自己的 rolling baseline。不同選手之間不直接比較分數。

結果與原因分離

validFirstShot 與 counterstrafeSuccess 是結果；曝光、急停過程、開火與瞄準指標用來解釋原因。

不丟棄行為失敗

早開火、未曝光、未 counter、timeout 都是訓練結果，留在 operational denominator；只有技術污染才排除。

不做單一總分

相同成功率可能來自完全不同的問題。輸出最多一至兩項主要診斷與一個可執行提示。

明確非目標

  • 不進 Assessment history、排行榜或跨玩家 percentile。
  • 不以固定的「職業級反應時間」門檻評價玩家。
  • 不把 20 個 presentation 當成 20 個獨立受試者。
  • 不讓補槍後擊殺掩蓋首發失誤。

3. 指標與資料契約

現有代表目前程式已有的欄位或可直接取得的 frozen derivation； 提議代表每日診斷需要新增或重新聚合； 已確認代表本輪已拍板的演算法語意； 待決策代表語意尚需共同拍板。

已確認的急停成功定義： counterstrafeSuccess = firstFire exists AND firstFire.residualSpeed < CS2_PROFILE.accuracyThreshold。 threshold 必須直接引用專案的 CS2_PROFILE.accuracyThreshold，不可在分析層複製第二個常數。 此結果只表示移動速度不再造成彈道失準；不保證滑鼠瞄準、recoil 或 spread 一定命中。

四組量測的計算規則

1. 看見 → 反向鍵

onsetToCounterMs = tCounter − tMeasurementOnsetMs

「看見」固定使用 50% visibility onset，不使用 target spawn 的 visible event。 負值保留為 anticipated，表示玩家在量測 onset 前已反向；缺少 counter 則保持 missing 並加 flag。

2. 急停成功

success = firstFire != null && firstFire.residualSpeed < accuracyThreshold

第一個進入 gate 的 tick 用來計算急停速度、距離與過度反向，但最終成功只看首發當下速度。 residualSpeed >= threshold 為 movement-inaccuracy risk；無首發標成 no_first_shot。

3. 曝光後瞄準

reaction + main movement + confirmation

依序計算 onset→aim-start、aim-start→first-on-target、first-on-target→first-shot； 同時輸出 dYaw/dPitch 路徑、角速度、epsilon curve、overshoot 與 reacquisition。

4. 首發與 killing shot

fire.shotSeq ↔ hit.shotSeq

首發命中由逐 trial 的第一發直接聚合。killing shot 分析命中前的滑鼠路徑、角誤差、速度與前一發 miss 的修正； 未擊殺 trial 保持 missing，另報分析 coverage。

急停成功率

counterstrafeSuccessRate = counterstrafeSuccessCount / presentationCount
counterstrafeSuccessWhenFiredRate = counterstrafeSuccessCount / firstShotCount

第一個是每日 operational 主指標：no-shot 仍留在 20 次分母中。第二個只回答「有開首發時，有多少次已低於速度門檻」。 兩者都儲存為 0–1，只有 UI 格式化為百分比。no_counter 是技術遵從 flag， 但不覆寫以首發 residual speed 為準的急停成功判定。

瞄準行為的兩條訊號

訊號代表什麼使用方式
dYaw/dPitch玩家實際滑鼠輸入造成的 tick-integral 視角變化計算 mouse path、angular velocity、修正方向與微調次數
epsilonDeg/onTarget包含玩家側移視差後，準心與目標的最終幾何關係計算 acquisition、overshoot、reacquisition 與 shot-time error

兩者不可互相取代：玩家側移時，即使滑鼠不動，目標在畫面上的角位置仍會改變。 因此手部輸入品質看 dYaw/dPitch，任務結果看 epsilonDeg/onTarget。

首發與 killing-shot 分母

operationalFirstShotHitRate = firstShotHitCount / presentationCount
conditionalFirstShotAccuracy = firstShotHitCount / firstShotCount
killingShotAnalysisCoverage = killedPresentationCount / presentationCount

killing-shot 指標是成功 trial 的條件式描述，不能單獨拿來評價整體瞄準能力； 必須搭配 coverage、timeout 與所有 miss 的首發行為，避免 survivorship bias。

4. 瞄準—急停策略辨識

分類單位是 presentation，不是選手。 每次 peek 先依事件順序分類，之後才以比例描述選手近期偏好。不要因為某天多數 trial 屬於一類， 就永久把選手標成該策略。

分類錨點

符號欄位定義
OtMeasurementOnset目標第一次達到 50% visibility 的 tick；「看到敵人」的量測錨點
MtAimStart沿用 sustained mouse-movement detection 的有效瞄準開始時間
AtStableOnTarget第一個連續至少 2 ticks onTarget=true 的區段起點
CtCounter反向鍵 counter event 的時間
GtAccuracyGatecounter 後第一次 |vx| < accuracyThreshold 的 tick
FtFirstShot該 presentation 的相容首發

A 不直接使用第一個單獨的 on-target tick，因為準心可能只是掃過目標。 初版用連續 2 ticks（128 Hz 下約 15.6 ms）定義 stable acquisition；正式凍結前應比較 2／3 ticks 的敏感度。

逐 presentation 分類規則

toleranceMs = 1000 / simHz；128 Hz 時為 7.8125 ms

tolerance 用來吸收 onset／acquisition 的 tick 量化誤差。落在容差帶內時不強迫判斷先後； 正式凍結前應以 0、1、2 ticks 重跑，確認策略比例不會因門檻微調而翻轉。

輔助驗證特徵

strategyOrderMs = tCounter − tStableOnTarget
aimPathBeforeCounterRatio = mousePath(O → C) / mousePath(O → F)
特徵先瞄準再急停先急停再瞄準用途
strategyOrderMs通常為正通常為負主要連續策略軸，不只保存離散類別
onTargetAtCounter通常 true通常 false驗證 counter 當下是否已完成瞄準
epsilonAtCounterDeg通常較小通常較大量化 counter 當下離目標多遠
aimPathBeforeCounterRatio通常較高通常較低當 stable acquisition 缺失時仍提供連續證據

5. 個人 rolling baseline

以下參數是第一版提案，不是已驗證門檻：至少 7 個合格 session 才啟用診斷，之後使用最近 14 個合格 session 作基準。

基準納入條件

  • 同一 drill id：peek_click_transfer_pilot_v1_2deg。
  • 相同 sensitivity model、武器／movement model、FOV 與關鍵場景版本。
  • 無 suspect、overflow 或資料契約錯誤。
  • session 未被手動標為熱身、測試設備或中途干擾。

比較方法

比例指標

使用「成功次數／嘗試次數」與 baseline 的 Beta posterior 比較，而非只比較百分點。

p_today ~ Beta(1 + x_today, 1 + n_today − x_today)
p_base ~ Beta(1 + Σx_base, 1 + Σn_base − Σx_base)

時間與距離

每日先聚合為 session median，再與 baseline session medians 比較，避免把同一天的 20 trials 當成 20 個獨立日。

robustZ = 0.6745 × (today − baselineMedian) / baselineMAD

狀態建議

狀態第一版規則呈現方式
穩定未達 practical change，或 posterior／robust deviation 證據不足「落在近期正常波動」
觀察單日出現具實務大小的偏離，但尚未持續指出變化，不給強制處方
需要介入大型單日偏離，或最近 3 天至少 2 天同方向異常輸出一項主要診斷與一項訓練提示

Practical change 必須先由真人資料校準；初版不應硬寫成「10 ms 一定有意義」或「少 1 次命中就是退步」。 在資料不足前，只顯示原始值與趨勢，不產生紅燈。

6. 根因診斷規則

診斷按照因果時間順序評估，優先回報最早的異常環節。後段結果可能只是前段失敗的結果， 例如 gate 前開火已足以解釋首發命中下降時，不再把「瞄準失常」列為第一診斷。

優先序判斷訊號診斷標籤教練提示範例
1no_measurement_onset 或 timeout-before-onset 增加曝光完成度下降先完成乾淨曝光，不急著找首發速度。
2onset→counter 變慢，或 no_counter 增加反向啟動遲疑看到目標即反向；本組暫不追求快槍。
3counter→gate、stop distance 或 over-reversal 變差急停過程效率下降縮短同向鍵拖延，避免反向壓過頭。
4counterstrafeSuccessRate 下降，且 onset→shot 同時變快用移動準確率交換速度把第一發延後到 residual speed 低於 accuracy threshold。
5gate 後首發仍 miss，first-shot error 增加首發瞄準下降維持停穩節奏，調整出掩體預瞄落點。
6gate→shot 變慢，但命中率不變停穩後過度確認小幅提前 commit，確認準確率能否維持。
7上述問題集中於單側且跨日持續左右技術不對稱弱側另做技術組；正式診斷組仍維持 L/R 平衡。

診斷排序

  1. 先排除技術污染，否則不做技能歸因。
  2. 找出相對 baseline 有實務大小且有趨勢支持的異常指標。
  3. 依上表時間順序選出最早的異常環節。
  4. 最多顯示兩個 finding；第一個必須有直接 evidence。
  5. 每個 finding 只配一個當天可以執行的訓練提示。
速度—準確率保護：若 onset→shot 變快，但 valid-first-shot posterior 同時下降， 不判定為速度進步；標記為「速度交換」。只有成功率穩定時，時間縮短才算有效改善。

8. 現有實作風險與必要修正

首發命中率語意不一致：transfer aggregate 目前沿用 counter-strafe 的 firstShotHitRate，但該值以 peek.outcome === 'hit' 聚合。 在允許補槍的 drill 中，這其實可能是「最終擊殺率」。每日診斷必須改由逐 presentation 的 firstShotHit 重新聚合，並另設 killBeforeTimeoutRate。
風險影響提議處理
validFirstShot 不要求存在 counter event功能成功與技術遵從混在一起依本輪決定同時保留 functional 與 protocol-compliant 結果；首頁以 functional 為主，技術遵從作 evidence。
rate 有 0–1 與 0–100 兩種慣例UI 格式化可能造成 100 倍誤讀資料契約一律存 0–1，UI 才格式化百分比，並在欄位文件寫明。
spawn-anchored 3000 ms timeout慢曝光者的 post-onset 可用時間較少同時報 no-onset、onset→hit 與 timeout；不可只分析成功 trial。
嚴格 L/R 可預測量到的是預期方向下的 execution，不是 choice reaction維持現有 drill 定位；報表文字不可稱為一般視覺反應速度。
單日每側只有約 10 次L/R 差異波動很大單日只顯示，跨日趨勢才診斷。
目前沒有 coach-facing transfer section計算存在但尚未形成每日使用閉環演算法拍板後再接 ResultScreen／history，避免 UI 先凍結未定義語意。

9. 已確認與下一輪待拍板

已確認 — 急停成功的唯一結果判準

首發存在且 firstFire.residualSpeed < CS2_PROFILE.accuracyThreshold 才是急停成功。 曾經進入 gate、zero crossing、stop distance 與 over-reversal 都是過程證據，不可取代首發當下的成功判準。

已確認 — functional 與 protocol-compliant 結果並存

validFirstShot 以實際結果為主；另保留 protocolCompliantValidFirstShot 檢查是否觀測到正確 counter。前者放首頁，後者用於診斷 evidence。

Q1 — 個人基準窗口用 7/14 是否合適？

提案為至少 7 個合格日後啟用，使用最近 14 個合格日；也可改為 10/20，以較慢但更穩定的方式更新。

Q2 — corridor exceeded 是失敗還是排除？

建議 operational rate 中算失敗，但另報 protocol-clean rate，避免刪掉真實移動控制問題。

Q3 — 每日只給一項還是最多兩項訓練提示？

我的偏好是首頁只給一項；第二項放在展開的 evidence 區，避免同一天同時修改太多動作。

Q4 — 是否加入主觀狀態資料？

可選擇記錄睡眠、疲勞、手感或疼痛，但應只作 context，不用來覆寫客觀量測。

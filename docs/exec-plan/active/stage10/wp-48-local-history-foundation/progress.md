## Decision Log

- **D-48.P1 / payload seam**：自動保存必須使用 render-loop completion 已建立、同時供 metrics/diagnosis/Result Screen 使用的**同一個 `ExportPayload`**；不得二次 snapshot/build。
- **D-48.P2 / schema trust**：`sessionHistoryLoader.ts` 現有 shallow `isExportPayload()` 不足以保護 filesystem/API；T1 建立單一 strict runtime parser，舊 loader 改用它。
- **D-48.P3 / source of truth**：JSON 是唯一 source of truth；memory index/cache 皆可重建，不引入 DB。
- **D-48.P4 / identity**：run identity 使用 schemaVersion + Participant ID + exact drillId + normalized startedAt；同 identity same content=idempotent，different content=conflict。
- **D-48.P5 / missing participant**：不使用 `anonymous`／`unknown` placeholder；沒有 Participant ID 就拒絕保存並顯示可行動狀態。
- **D-48.P6 / live loop isolation**：History API/client 不進 sim tick；保存失敗不影響 Result metrics、session progression 或 determinism。
- **D-48.P7 / Assessment-only archive**：只有 `meta.assessment !== undefined` 的 payload 可以建立歷史紀錄。Practice 仍是合法 `ExportPayload`，但 client 回 `excluded` 且不送 request；repository/API 對直接 submission 回 `PRACTICE_NOT_ARCHIVABLE`，不得建立任何檔案。此決策取代原本的 Practice 歷史／Participant context 規劃。
- **D-48.P8 / OQ-48.1 hosting（T0 凍結，使用者確認）**：Node History API 採 **Vite `configureServer`/`configurePreviewServer` middleware**（Option A）。理由：PoC 4 證實 close hook 可靠釋放 root lease，且與現有 `coopCoep()` plugin 同型，不需新增 process orchestrator。標記為 conscious technical debt（README §3.2 #1）；`historyApi.ts` handler 需與 hosting 解耦，未來要換 standalone process 時可重用。
- **D-48.P9 / OQ-48.2 history root（T0 凍結，使用者確認）**：history root 正式凍結為 `<repo>/data/session-history/`。browser UI 不接受路徑輸入；production 預設路徑由 server 端解析，可用 `FPS_HISTORY_ROOT` 環境變數覆寫（僅供 test/Playwright 使用，見下方 root 注入計畫）。
- **D-48.P10 / T1 canonical serializer**：`canonicalExportJSON` 採遞迴 key 排序（`JSON.stringify` 前對每個物件的 key 做 `Array.sort()`），陣列元素順序保持不變，而非手動複刻 `Meta` 逐欄位順序。理由：語意等價、更簡單（Rule 0），且對任何未來 additive optional 欄位自動成立，不需要每次新增 Meta 欄位都同步更新 canonical 排序表。
- **D-48.P11 / T1 spawn 欄位驗證邊界**：`SpawnMeta.motion`／`spawnArea`／`spiderShot`／`spawnDelayMsRange` 在 `metadata.ts` 本身即宣告為 `unknown`（opaque contract，WP-36 comment）；parser 對這些欄位僅原樣傳遞、不深入驗證，只驗證型別具體的 `seed`（必填 finite number）與 `presentationMs`（選填 finite number）。與現有 `collectMeta()` 對 `spawn` 完全不驗證（直接 passthrough）的既有行為相容，不新增比原本更嚴格的隱性契約。
- **D-48.P12 / tsconfig.node.json 需要 DOM lib（偏離 T0 規劃）**：T0 規劃的 `lib: ["ES2022"]`（無 DOM）在實作時對 `tsc --noEmit -p tsconfig.node.json` 直接失敗——`server/history/HistoryRepository.ts` 對 `src/data/exportPayloadSchema.ts` 只做 `import type`，但 TS 仍會把該檔案（以及它 type-only import 的 `export.ts`／`metadata.ts`／`resolutionMode.ts`／`eligibilityGate.ts`／`createRenderer.ts` 等）整份拉進同一個 program 做完整型別檢查，即使只用到型別。這些檔案的**執行期**程式碼（非型別位置）引用了 `document`／`Blob`／`URL`／`navigator`／`HTMLCanvasElement`／`FrameRequestCallback` 等 DOM 全域（如 `export.ts` 的 `downloadTextFile()`、`metadata.ts`/`resolutionMode.ts`/`eligibilityGate.ts` 的 `globalThis.navigator`/`requestAnimationFrame` 讀取），沒有 DOM lib 就是一批 `TS2304`/`TS7017`。改為 `lib: ["ES2022", "DOM", "DOM.Iterable"]` 後 0 錯誤。這不違反 FR-48.10（bundle 不得含 `node:*`／history root）——FR-48.10 管的是**瀏覽器打包產物**的內容，不是 Node 端 tsc 用哪個 lib 做型別檢查；`server/` 執行期程式碼本身從未引用任何 DOM 全域。
- **D-48.P13 / vite.config.ts 延後納入 Node typecheck boundary（偏離 T0 規劃）**：T0 規劃 `include: ["server", "vite.config.ts"]`，實作時發現把 `vite.config.ts` 納入會讓 `tsc -p tsconfig.node.json` 因既有、與 WP-48 無關的問題失敗：`vite.config.ts` 頂部 `/// <reference types="vitest/config" />` 依賴 vitest 對 `vite` 模組的 `declare module 'vite' { interface UserConfig { test?: ... } }` 全域擴增（讓 `defineConfig({ ..., test: {...} })` 型別合法），但在本專案的 vitest 2.1.9 + vite 6.4.3 + TS 5.9.3 組合下，即使該擴增檔案確實被載入（以 `--traceResolution`／移除 `skipLibCheck` 交叉驗證過，`chunks/vite.CzKp4x9w.d.ts` 有被處理，同批次還冒出 `chai` 型別缺失錯誤佐證），`defineConfig` 的 overload 解析仍看不到 `test` 屬性，判斷是模組識別（module identity）在 `bundler` resolution 下沒有和 `vite.config.ts` 的 `import { defineConfig } from 'vite'` 合併成同一份 `UserConfig` interface 的既有第三方型別相容性問題，與本次要新增的 `HistoryRepository` 無關。這件事在 T0 規劃前從未被驗證過——`tsconfig.json`（瀏覽器）的 `include` 只有 `["src"]`，`vite.config.ts` 從未被 `tsc` 檢查過，只靠 Vite 自己的 esbuild（不做型別檢查）跑；T2 是第一次把它排進任何 tsc program。依 Scope Discipline（本次任務只需要讓 `server/` 有型別邊界），`tsconfig.node.json` 的 `include` 先只放 `["server"]`；`vite.config.ts` 何時真的需要被 Node typecheck boundary 覆蓋、以及上述 vitest/vite 型別相容性問題如何解，留給 T3（`historyPlugin.ts` 掛載進 `vite.config.ts` 時）處理並記錄。

- **D-48.P14 / T3 loopback + 413 policy**：`createHistoryApiMiddleware` 對非 loopback 呼叫端（`req.socket.remoteAddress` 不在 `127.0.0.1`／`::1`／`::ffff:127.0.0.1`）一律當成「路由不存在」直接 `next()`（不是回一個帶 error code 的 403）——理由：`HistoryApiErrorCode`（`src/history/contracts.ts`,T1 已凍結）沒有對應的「非授權呼叫端」代碼,新增一個會擴大契約面且此路徑不在 FR-48.4 的六 routes 之列;讓非 loopback 呼叫端得到與「路徑不存在」一樣的 404,不洩漏 API 存在與否,同時维持 NFR-48.5。同一 fallback（`next()`）也用於「`/api/history` 前綴下但不匹配六個 routes」的請求,理由相同（README 只承諾六個 typed routes,其餘不需要一個新的 error code）。16 MiB 限制採雙層防禦：先查 `Content-Length` header（若存在且超限,完全不讀 body 就回 413）,再用逐位元組計數器兜底 chunked/無 Content-Length 的請求——兩者都符合「不可先無界限 buffer」（README §2.4／T3.md）。
- **D-48.P15 / T4 fixture split（`payloadFixtures.ts`）**：把 `makeAssessmentPayload()` 從 `tests/history/testHelpers.ts` 拆到零 `node:*` import 的 `tests/history/payloadFixtures.ts`，`testHelpers.ts` re-export 保持 T2/T3 既有 import 不變。理由：T1 已證實 tsc 會把整份被 import 的檔案拉進同一個 program（即使只用一個 export），`src/history/*.test.ts` 在 `tsconfig.json`（無 `types:["node"]`）下若直接 import 含 `node:fs`/`node:os`/`node:path` 的 `testHelpers.ts` 會 TS2307。同一限制也讓「監聽 `process.on('unhandledRejection', ...)` 並斷言為 0」這個 T4 DoD 項目無法寫進 `src/history/HistoryPersistence.test.ts`，改成獨立 Node-typed 測試 `tests/history/historyPersistenceUnhandledRejection.test.ts`；`src/history/HistoryPersistence.test.ts` 本身改用「`save()` 對每種失敗都 resolve 而非 reject」的結構性斷言覆蓋同一行為的 browser-typeable 一半。此拆分模式可直接沿用於未來任何需要在 `src/history/*.test.ts` 建 fixture 的 task（含 T5）。
- **D-48.P16 / T4 retryable 判定含 423（超出 T4.md 步驟 3 字面表列）**：T4.md 步驟 3 只列「network/timeout/5xx retryable；invalid export/practice not archivable/missing participant/conflict non-retryable」，未提及 423。實作時把 `HISTORY_ROOT_LOCKED`（423）也歸類為 retryable——理由：root lease 由另一個 process 持有是暫時性狀態（另一個 dev/preview server 關閉後會釋放），語意上與 5xx 的「暫時性服務不可用」相同，不像 400/404/409/413/422 是「同樣輸入必然再次失敗」。`HistoryClientError` 的 retryable 判定改用一張顯式 code 對照表（`NETWORK_ERROR`／`TIMEOUT`／`STORAGE_IO`／`HISTORY_UNAVAILABLE`／`HISTORY_ROOT_LOCKED` = retryable，其餘皆否），而非只看 HTTP status class，以涵蓋 423 這類語意上非 2xx/5xx 但實際暫時性的 code。

- **D-48.P17 / T5 E2E 策略：dev-only `__fpsTest` hook 取代 live-singleton 完整 drill**：`saveToHistory(overrides?)`／`historySaveState()`／`retryHistorySave()` 直接呼叫 `main.ts` composition root 的真實 `historyPersistence` 單例,對 harness 合成 payload 疊加 Participant/assessment envelope。理由：`__fpsTest` 本身是與 live `renderLoop` 隔離的獨立 pipeline（`fpsTestHarness.ts` 檔頭既有說明),不會觸發 completion IIFE 的 `phase==='ended'` 分支;要用真實 pointer lock 驅動 live 單例走到 `ended` 依專案既有慣例不在自動化 E2E 範圍（`full-drill.spec.ts` 標頭)。此法讓 E2E 仍能對真實 `HistoryClient`→Node API→temp root 路徑斷言,只是繞過「由 live render loop 觸發保存」這一小段 wiring,以程式碼檢視 + 既有 36 條 E2E 的零回歸間接佐證。與既有 `showResult()` test-only hook 同一慣例（截至 T5,兩者皆 `import.meta.env.DEV` 守衛、production 剝除)。

- **D-49.P28 / T4 first-shot hit outcome verified directly, not via `firstShot.hit`**：`spider-v2.peripheral-first-shot-hit-rate` 的分子由 `PeekWindowTs.firstFire` 的實際 hit outcome（`fire.hit || matching shotSeq hit event`）算出，**不**重用 `deriveSpiderShotMetrics(payload).firstShot[].hit`——該欄位讀的是 `window.outcome==='hit'`（整個 window 內任一發命中就算，含補槍），與研究設計文件 §risks 明確指出的誤判風險一致。理由：文件給了兩個修法選項（projector 直接驗證，或先修正 canonical derivation）；後者會動到 `spiderShotMetrics.ts` 這個被即時診斷/HUD 共用的既有輸出，屬於超出 T4 範圍的跨模組變更且風險更高，故選擇前者——projector 內部小範圍重算，不碰共用 derivation。`fireAngleErrorDeg`／`overshootDeg` 兩欄未受此 bug 影響（讀的是幾何量而非 outcome 布林值），繼續直接重用。
- **D-49.P29 / T4 session-level condition cell 由 drill config 常數推導，不是每 payload 讀取**：`spider-shot-v2` 的 `targetConditionCell`（trend cohort identity 的一部分）在模組載入時由 `spiderShotV2`（`src/drill/spider_shot_v2.ts`）的 `angularRadiusDegRange`/hitbox/`peekTimeoutMs`/`endCondition` 算一次固定字串，不逐 payload 解析 `meta.spawn.spiderShot`（該欄位依既有慣例是「不解析」的 opaque echo）。理由：研究設計文件明確要求「session-level condition cell」（協定層級，非逐 trial 的 D_deg/W_deg），且 exact-id registry 保證同一 `drillId` 一定對應同一份程式碼內凍結的協定——用常數推導而非讀 payload 才是這個語意的正確實作；副作用是所有合格 `spider-shot-v2` run 只會因為其他 `CompatibilityKey` 欄位（sensitivity/FOV、weapon、feedback policy 等）分 cohort，不會因為個別 run 之間的抽樣抖動分裂 cohort。
- **D-49.P30 / T4 單一 run 允許部分 metric 缺席，不是 all-or-nothing**：`registration.project(payload)` 對每個指標各自嘗試計算，資料不足（如零周邊命中、無 tracking 樣本）時該指標從 `observations` 陣列省略，而非讓整個 run 的 projection 變成 `invalid-metric`。只有 canonical derivation 本身拋錯（如 malformed export 缺 tick）才讓整個 run 變 `invalid-metric`。理由：README §2.5 的 `HistoryProjectionResult.observations` 型別本身就是 `readonly MetricObservation[]`，沒有規定必須涵蓋全部 5 個 descriptor；`hits/min=0`（真的零命中）是有效資料，不該因為同一 run 缺 median-based 指標的樣本就整筆作廢。
- **D-49.P31 / T4 cursor 用 `(startedAt, runId)` 定位而非 index**：`HistoryAnalysisService` 的 opaque cursor 編碼上一頁最後一筆的 `{startedAt, runId}`，下一頁請求時在當前 `listRuns()` 結果裡重新找到該筆的 index 再 +1，而不是直接編碼一個整數 offset。理由：`HistoryRepository` 沒有持久化的穩定排序 index（每次呼叫 `listRuns()` 都是即時排序整個 in-memory 集合），純數字 offset 在 run 集合於分頁之間發生變化時會靜默錯位；用內容定位在找不到該筆時能明確回 `invalid-cursor`，而不是悄悄回傳錯誤的一頁。
- **D-49.P32 / T4 HistoryTrend 的 cohort id 用固定 9 欄位 join，不用 `JSON.stringify`**：`cohortKeyId()` 手動列出 `TrendCompatibilityKey` 的 9 個欄位（明確 order）join 成字串，而非 `JSON.stringify(key)`。理由：`JSON.stringify` 的 key 順序不是 `TrendCompatibilityKey` interface 契約的一部分，未來欄位重新排列或引擎版本差異都可能讓語意相同的 key 產生不同字串；固定欄位 order 的 join 是本模組自己控制、可稽核的身分函式。

- **T0 CodeGraph 追加發現**：`historyMetricsFor`、`resultShown`、`currentHistorySession`、`buildCurrentExportPayload`、`resultScreen`（`main.ts` 內的 completion-seam 相關符號）全部**無 direct covering test**——與 WP-48 README §0 point 9 對「`main.ts` completion wiring 無直接單元測試」的既有結論一致，但範圍更廣；T3/T5 的 Playwright E2E 覆蓋比重因此更重，不可只靠 unit test 斷言 wiring 正確。
